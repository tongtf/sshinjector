## 1. 逐项改法

### A · P0-2（chip 快照化）

1. `TunnelManager` 新增**不可变** `data class ExitSnapshot(id, label, serverHost, health, activeConnections, connTotal, failTotal, degradeTotal, lastError, startedAt)`。
2. `exitsState: StateFlow<List<ExitSnapshot>>`；`publishExits()` = `exits.values.map { it.toSnapshot() }`（每次新实例 → `StateFlow` 按值比较会发射）。
3. `noteDegraded/noteRecovered/startExit/stopExit/stopAll` 后 publish；`VpnController.evaluateExitHealth` 修改 health 后**显式** publish（通过 `tunnelManager.publishExitsNow()` 或 `noteDegraded/noteRecovered` 已覆盖的路径）。
4. `MultiExitViewModel` 的 `Data.runtime: Map<String, ExitSnapshot>`；`ExitRuntimeUi` 从快照构造（不再读 `plugin`）。
5. 测试：`TunnelManagerExitTest` 增加“`exitsState` 在 `noteDegraded` 后**收到新值**”（`async { exitsState.drop(1).first() }` + `withTimeout`）。

**方案审计**
- 风险：`ExitSnapshot.activeConnections` 是发布时快照，连接数在两次发布之间不更新（可接受；健康/启停会刷新）。
- 风险：`TunnelManagerExitTest` 原断言 `exitsState.value.single … health` 仍成立（类型改）。
- 规避：保留 `exitsSnapshot(): List<ActiveExit>` 给诊断/健康（内部用），UI 只用 `ExitSnapshot`。

### B · P0-1 + I-2/I-5/I-6/F8

1. **P0-1**：`VpnController` 增加 `private val reconcilerScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)`；把 `init` 的 `allExitsFlow` collector 移到该 scope；collector 内保留 `if (!isRunning) return@collect`。不随 `cancelChildren()` 取消。
2. **I-2**：`protectDatagramChannel`、`excludedRoutes`、`transportMode` 加 `@Volatile`（`transportMode` 的读写都走它）。
3. **I-5**：`connect()` 的 `catch (Exception)` 前加 `catch (e: CancellationException) { withContext(NonCancellable) { disconnect() }; throw e }`。
4. **I-6**：`connect()` 里 4 个 TUN 丢弃计数 `set(0)`（`droppedTunControlPackets/Bytes`、`trailingBytesDropped`、`droppedNoTun`）。
5. **F8**：`forwardDnsBypassPacket` 的 `responseBuf` 512 → 4096，并校验响应 ID 与 `pending.originalQueryId`（若不匹配丢弃 + 计数）。

**方案审计**
- 风险：独立 scope 的 collector 在 `VpnController` 生命周期内不取消；它是 singleton，进程级生命周期，可接受。
- 风险：collector 在未连接时也会收到出口表发射 → `isRunning` 早退；不刷新快照（下次 connect 会 `refresh`）。
- 风险：`NonCancellable { disconnect() }` 在 `disconnect` 内部再 `cancelChildren()`（对已取消上下文无副作用）；`stopAll` 是 suspend，在 NonCancellable 中可执行。
- 风险：F8 放大缓冲后仍可能超 4096（极长 TXT）；置 TC 或截断策略本批不做，保持 4096（与受保护 socket 一致）。

### C · F1/F6/I-14

1. **F1**：新增 `private fun nextQueryId(): Int = queryIdCounter.updateAndGet { if (it >= 0xFFFF) 1 else it + 1 }`；两处 `incrementAndGet()` 改用它；`setID(queryId)` 保留（值已保证 1..65535）。测试：把计数器推到 65535 后断言下一次为 1（暴露 `internal fun nextQueryIdForTest` 或 `internal` 函数）。
2. **F6**：非 A/AAAA 重建查询时 `msg.header.setFlag(Flags.RD.toInt())`（EDNS OPT 复制本批不做，记 1.4）。
3. **I-14**：`pendingResponses = Channel(2048)`；新增 `offerDnsResponse(resp): Boolean`（`trySend` 失败 → `droppedDnsResponses.incrementAndGet()` + 10s 节流 WARNING），6 处 `trySend` 改调它；`diagnostics()` 增 `DNS 应答丢弃 N`。

**方案审计**
- 风险：ID 回绕后可能与在途查询重号（65535 条在途不可能；`pendingQueries` 通常 < 百）。
- 风险：ID 从 65535 回到 1 时客户端 `originalQueryId` 不变（那是客户端 ID，独立）。
- 风险：`Channel(2048)` 在 TUN 停摆时会丢应答；客户端会重试；计数可见。可接受。
- 风险：`offerDnsResponse` 的 6 个调用点都忽略返回值；改为计数即可，不改控制流。

### D · F3/F4/F5/I-11 + bypass 退避

1. **F3**：三处 SYN-ACK 写点改为 `val ok = tunWriterProvider()?.write(pkt) ?: false; if (ok) conn.synAckWritten = true`；失败时**不**置位（回程继续排队；客户端重传 SYN 会补发）。
2. **F4**：`flushReturnBatch` 返回 `Boolean`；`writeTcpPayloadToTun` 在**释放 `downlinkLock` 之后**若失败 → `closeTcpConnection(conn.key, conn, notifyBrowser = true)`（RST），并 return。
3. **F5**：`processTcpPacket` 解析后：`if (dataOffset !in 20..60 || dataOffset > payloadLength) { droppedMalformedTcp++; return }`（计数进快照可选）。**先校验再读选项**，避免 `position()` 越界。
4. **I-11**：`UdpRelay` 增加 `AtomicLong(lastDropLogAt)` + CAS 门；只有通过门才 `portBreakdown()` 并 `VpnController.appLog(...)`（不再调 `appLogThrottled`，避免双重节流）。
5. **bypass 退避**：`RELAY_IDLE_SLEEP_MAX_MS` 8 → 50（仅降低空闲唤醒；独立线程池留 1.4）。

**方案审计**
- 风险：F3 不置 `synAckWritten` 时，若 SYN-ACK 被丢且客户端**不重传**（极少），连接会停在 SYN_SENT；但 TCP 必然重传 SYN。
- 风险：F4 在 relay 线程内 close（持锁外）；`closeTcpConnection` 会发 RST 并 notify；不会与 `downlinkLock` 嵌套（已释放）。
- 风险：F5 若 `dataOffset` 合法但 `payloadLength` 小于 20（纯 ACK 无载荷时 `payloadLength` 仍是 TCP 头长度，≥20），不会误杀。需用 `payloadLength`（IP 载荷）而非 `payloadLen`（数据）。
- 风险：I-11 的 CAS 门与 `appLogThrottled` 的语义不同（10s 窗口）；保持原 `DROP_LOG_INTERVAL_MS`。
- 风险：退避 50ms 会增加空闲回程延迟（有数据即复位，仍零延迟）；可接受。

### E · 服务/持久化/UI

1. **I-4**：`teardownSession` 补 `poolFailReconnectPending = false`（与 `disconnectInternal` 对齐）。
2. **F2**：`whitelistSelection()` 过滤：跳过自身包名 + `getApplicationInfo` 失败（未安装/不可见）的包；过滤后为空 → 返回空列表（`dnsTransportFor` 自动 SYSTEM、`buildVpnBuilder` 不加路由）；记录 WARNING（`白名单应用均不可见 · 已按全部直连处理`）。
   - 抽纯函数 `effectiveWhitelist(packages, ownPackage, isInstalled)` 放 `domain/vpn` + 单测（3 例）。
3. **I-3**：`Socks5TunnelPlugin.socksServer`、`_socksAuth` 加 `@Volatile`。
4. **I-7**：`saveServerEdit` 把 `existingId == 0L` 也视为新建；`getByIdBlocking(existingId) == null` 时 `throw IllegalStateException("服务器已被删除")`（UI 已有 catch）。
5. **I-8**：`SettingsDataStore.clearLastServerId()`（`edit { it - KEY }`）；替换 3 处 `setLastServerId(0)`（service 两处、ServerDeleter）。
6. **D-2**：`UiState.dnsMode` 改 `Int`；Dashboard 配色按 int；文案 `stringResource(dnsModeLabelRes(mode))`（新增映射）。
7. **A10**：`startVpnService`/`disconnect` 的 `startService` 包 try/catch；失败时回滚乐观 `Connecting` 并写 WARNING。
8. **I-9**：`SettingsDataStore.setStatsState(ad, added, removed)` 单次 `edit` 写三键；`StatsListApplier.writeState` 改用它。
9. **D-19**：`AppUidResolver.request` 对两个 `ByteArray` 做 `copyOf()`（16B×2/连接），并 `require(len==4||16)`。

**方案审计**
- 风险：F2 在 `whitelistSelection` 做 PM 查询（connect 的 IO 协程内），包多时 ms 级；可接受。过滤后 `whitelistPackages` 变空 → `setWhitelistPackages` 日志/策略随之变化，一致。
- 风险：I-7 抛异常会走 `ServerEditViewModel` 的 catch（提示"加密失败，请重试"文案不准确）；需在 UI 层把异常文案区分，或保留静默但记录 WARNING。**决定**：抛异常并在 `ServerEditViewModel` 的 catch 中显示 `e.message`（改文案）。
- 风险：I-8 `clearLastServerId` 后 `Flow<Long?>` 发 null；`BootReceiver` 已用 `?: 0` 兼容；`SshVpnService.autoReconnect` 的 `(first() ?: 0) == 0` 兼容。
- 风险：D-2 改 `UiState.dnsMode` 类型会影响所有读取点（仅 Dashboard），编译期可查。
- 风险：I-9 单次 `edit` 可能触发一次 Flow 发射（三键），比三次少；无行为回归。
- 风险：D-19 每连接多 32B 复制；可忽略。
- 风险：A10 失败后回滚 `serverConnectionStatus`（用 `clearConnectingStatus`，已有）。

## 2. 方案级二阶风险审计（重点）

| # | 方案可能引入的新问题 | 结论 / 规避 |
|---|---|---|
| R1 | P0-1 独立 scope 的 collector 在 `stopExit` 时与 `connect` 并发 → 误停刚启动的出口 | 已存在 `staleExitIds` + `desired` 复核；collector 先 `delay(200)`；`stopExit` 幂等；保留 |
| R2 | P0-2 `ExitSnapshot` 每次 publish 新实例 → 高频分配 | 只在启停/健康变化 publish（非每连接）；出口 ≤5，可忽略 |
| R3 | F1 ID 回绕 65535→1 与极端在途重号 | 在途上限受 30s `pendingQueries` 清理约束（远 < 65535）；可忽略 |
| R4 | F2 过滤后为空 → 与 `buildVpnBuilder` 的 `isWhitelistMode` 判据不一致 | 过滤放在 `whitelistSelection`，TUN 与 DNS 策略读**同一**列表；两处都按空列表退化 |
| R5 | F3 不置 `synAckWritten` 后，回程缓存可能被 512KB 上限打满 | 客户端 SYN 重传是毫秒~秒级；队列上限已有溢出计数；可接受 |
| R6 | F4 在 relay 线程 close，可能重入 `downlinkLock` | close 在**释放锁后**调用；`closeTcpConnection` 内部再取 `downlinkLock` 是同线程重入（Java monitor 可重入），不会死锁；已在方案中明确“锁外 close” |
| R7 | F5 用 `payloadLength` 校验 `dataOffset`，可能误杀合法包 | 合法 TCP `dataOffset` 20..60 且 ≤ IP 载荷；加单测覆盖 SYN 选项/纯 ACK |
| R8 | I-6 清 TUN 计数可能与 `emitDataPlaneSnapshot(force)` 的取样顺序冲突 | 清零在 `connect()` 开头（会话开始），快照在断开前；无交叉 |
| R9 | I-7 抛异常改变 `saveServerEdit` 契约（原静默返回 0） | 仅在“行已被并发删除”时抛；UI catch 显示；补单测 |
| R10 | I-8 改 null 后，旧版本写下的 `0` 仍可能存在 | `Flow<Long?>` 读到 0 的旧值；消费点已按 `?:0`/`>0` 处理；新增 `clear` 只影响新写入 |
| R11 | D-2 改 Int 后，UI 文案映射漏语言 | `dnsModeLabelRes` 用现有 4 份资源；`StringResourceParityTest` 兜底 |
| R12 | I-14 有界 Channel 在突发 DNS 时丢应答 | 客户端重试；新增丢弃计数 + 节流 WARNING；上限 2048 远高于正常并发 |
| R13 | 并行批次的文件冲突 | 批次文件集**不相交**（见 §0）；`VpnController` 只归 B，`TcpStateMachine` 只归 D，`SettingsDataStore` 只归 E |
| R14 | 单测因类型/契约变化失败 | 每批先跑相关测试；A 改 `TunnelManagerExitTest`，E 改 `ServerRepositoryTest`/`ServerEditViewModelTest` |

**审计结论**：未发现会引入新 P0 的路径；R6/R7/R9 已在方案中加了约束（锁外 close、`payloadLength` 校验、UI 文案）。可以并行执行。

## 4. 实施结果 (2026-11-26)

5 批全部落地，门禁全绿：**587 单测** / ktlint / detekt / lint / assembleDebug / assembleRelease。

| 批 | 结果 / 偏差 |
|---|---|
| A | `ExitSnapshot` + 该发就发；补 2 条 collect/连接数测试；`MultiExitScreen` 无需改 |
| B | `reconcilerScope`（init 前声明）；3 个 volatile；取消 rethrow；TUN 计数清零；DNS 旁路 4096 + 事务 ID 校验；对接 `publishExitsNow()` |
| C | `nextQueryId` 1..65535 回绕；非 A/AAAA 补 RD；应答队列 2048 + `offerDnsResponse` 计数；测试里 `while` 条件多调一次导致 +2，已改为循环内 break（测试 bug，不改生产） |
| D | `writeSynAck` 唯一写入口；写失败不置位；重传成功后异步补 flush（单 flusher 互斥）；批量失败锁外关连接；`dataOffset` 校验 + `畸形 TCP` 计数；UDP 日志本地节流；bypass 退避 8→50ms |

**已知偏差（均为必要）**
- E 额外改了 `ConnectivityAppUidResolver`：`request` 的复制/校验在接口默认实现里，子类必须覆写 `enqueue` 才生效。
- D 新增 `畸形 TCP N` 计数与 `flushPendingReturnAsync`（F3 写失败后的排空触发点），均补了测试。
