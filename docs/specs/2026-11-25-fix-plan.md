### P1-1 早期失败：终态 + 归因只打一次

**改法**

1. `VpnController` 新增：
   ```kotlin
   fun reportConnectFailure(step: HealthStep?) {
       updateState {
           it.copy(
               status = VpnState.VpnStatus.Failed,   // 必须在 disconnectInternal 之后调用
               verified = false,
               failedStep = step,
               connectStage = null,
           )
       }
       emitSessionSummaryOnce()
   }
   ```
2. `SshVpnService.connect` 的 catch 顺序保持"先清理、后置终态"，把最后一行换成：
   ```kotlin
   disconnectInternal(userInitiated = false)
   vpnController.reportConnectFailure(mapConnectFailureToStep(e.message))
   ```
   （删掉临时的 `serviceVpnState.value = Failed` —— 它本来就会被 controller 观察者覆盖。）
3. `AppMetrics` 增加本会话幂等：
   ```kotlin
   @Volatile private var summaryEmitted = false
   fun summaryOnce(): String = synchronized(this) {
       if (summaryEmitted) return ""
       summaryEmitted = true
       summary()
   }
   fun resetSession() { summaryEmitted = false; ... }
   ```
   `disconnect()` 末尾改调 `summaryOnce()`；`reportConnectFailure` 也调它。**不要**把 summary 移到 `if (!isRunning) return` 之前，否则 forceReset/重复 disconnect 会重复打印。

**为什么用 Failed 而不是 Disconnected**：`observeVpnControllerState` 收到 Failed 会走 `disconnectIfIdleOnFailure`，但那时 `hasLiveSession = false`（清理已完成），`shouldCleanupFailureSession` 返回 false → 不会二次拆。顺序必须是"清理 → 发 Failed"。

**测试**：`AppMetricsTest` 增加"summary 只输出一次"；`reportConnectFailure` 的 state 变换抽成 internal 纯函数测试（status/failedStep/connectStage 三个字段）。

### P1-13 孤儿出口（不改全局代际）

**改法**

1. `TunnelManager.stopExit`：只 `exits.remove` + `Stopped` + `plugin.disconnect()`，**不递增 `sessionGeneration`**。
2. `TunnelManager.startExit`：在 `plugin.connect()` 返回后、置 Ready 之前：
   ```kotlin
   if (exits[id] !== entry) {
       runCatching { plugin.disconnect() }
       return Result.failure(IllegalStateException("Exit $id stopped while starting"))
   }
   ```
   三个分支（成功 / 失败 / 异常）都做同样复查；`stopAll` 的全局代际逻辑保持不变。
3. `Socks5TunnelPlugin` 增加 `@Volatile private var closing = false`：`connect` 开头置 false；`proxy.start` 成功后若 `closing` 已为 true → `proxy.stop()` + `client.disconnect()` + 返回失败。`disconnect()` 置 true。这样"stopExit 发生在 connect 完成前"时，新监听的 SOCKS 服务器也不会漏。

**为什么不用 `sessionGeneration++`**：代际是全局的，禁用一个出口会把**其它正在启动**的出口一并判为过期（`startExit:122`）→ "禁用 A，B 也启动失败"。身份复查是 per-entry 的，语义正确。

**测试**：`TunnelManagerExitTest` 新增两例——
- `stopExit` during start → 条目不存在、disconnect 调用、late success 不复活；
- 同时启动 A/B，stopExit(A) 不影响 B 正常 Ready。

## B3 · 数据面

### P1-9 OP_WRITE 竞态（最小改动）

**改法**（`Socks5ProxyServer.kt`）

把 `handleWrite` 尾部的判空移进锁：
```kotlin
synchronized(backpressureLock) {
    if (pendingWrites.isEmpty() && key.isValid) {
        key.interestOps(key.interestOps() and SelectionKey.OP_WRITE.inv())
    }
}
```
- `sendReply` 保持"先 `add`、后在锁内置位"的顺序，**不要**把 add 移进锁（会拉长临界区）；
- **不要**把 `write`/`poll`/`addFirst` 移进锁（锁内不做 IO）。

**为什么这样就够**：`add` 一定发生在置位之前；若 `handleWrite` 持锁时判空为真，说明此刻队列确实空，之后 `sendReply` 的置位一定发生在释放锁之后，不会被清掉。

**测试**：`Socks5ReplyRaceTest`（有界压力）：真实 socket + 假隧道，10k 次「回环写 + 并发 sendReply」，断言所有应答都收到、无连接悬挂；用 30s deadline，不用无界循环。

### P1-8 上行 flush：写锁 + 队列优先，不引入新乱序

**现状问题（推演结论）**：`flushPendingUpstream` 写 0/异常后把数据放回队首并继续自旋；而 `markEstablished`（`:2298-2299`）早于 flush 置 `Established` + 挂 `socksChannel`，packetLoop 的新数据可能走 `forwardToSocks` 直接写通道 → 旧队列被越过。简单 return 会让数据永久滞留。

**改法**

1. `TcpConnection` 增加 `val uplinkWriteLock = Any()`（普通对象，不参与 `synchronized(conn)` 的锁序）。
2. `flushPendingUpstream(conn: TcpConnection): Boolean`（返回是否已排空）：
   ```kotlin
   while (true) {
       val data = synchronized(conn.pendingUpstreamLock) {
           conn.pendingUpstream.removeFirstOrNull() ?: return true
       }
       var written = 0
       synchronized(conn.uplinkWriteLock) {
           val buf = ByteBuffer.wrap(data)
           try {
               while (buf.hasRemaining()) {
                   val n = channel.write(buf)
                   if (n == 0) break
                   written += n
               }
           } catch (e: IOException) {
               restoreToQueue(conn, data, written)      // 未写部分放回（用于统计）
               closeTcpConnection(conn.key, conn)        // 通道已坏：数据无法交付，让客户端重连
               return false
           }
       }
       if (written < data.size) {
           synchronized(conn.pendingUpstreamLock) {
               conn.pendingUpstream.addFirst(data.copyOfRange(written, data.size))
               conn.pendingUpstreamBytes += (data.size - written).toLong()
           }
           if (written > 0) { synchronized(conn) { conn.forwardedBytes += written }; sendAckToBrowser(conn) }
           return false                                  // **结束本轮**，不再自旋
       }
       synchronized(conn) { conn.forwardedBytes += written }
       sendAckToBrowser(conn)
   }
   ```
3. `forwardToSocks` 开头增加"队列优先"闸门（这是重试触发点，也是乱序修复）：
   ```kotlin
   if (conn.pendingUpstreamBytes > 0 && !flushPendingUpstream(conn)) {
       return 0        // 不 ACK、不消费；浏览器按 RTO 重传，重传包会再次触发这里
   }
   ```
   随后正常写时也走 `synchronized(conn.uplinkWriteLock)`。
4. 删除 `flushPendingUpstream` 原来的 `while(true)` + 异常后继续的逻辑；握手路径改为 `flushPendingUpstream(conn)`（返回值可忽略，失败已关闭连接或留待下次触发）。
5. 计数：`written==0` 不再累加 `upstreamBufferedBytes`（那是入队计数）；新增 `flushStallTotal`（可选，进快照）用于观测。

**为什么这是最优**
- 新数据永远在队列空之后才写 → 不会越过旧数据；
- 重传包天然是重试触发点 → 不需要额外协程/定时器；
- 通道坏 → 关闭连接（而不是无限抛异常），客户端立刻重连；
- 队列满/背压仍然连接局部，不阻塞 packetLoop。

**测试**（新 `TcpUplinkFlushTest`）
- 假 channel：前 3 次 `write` 返回 0，之后正常 → 断言数据按序到达、`forwardedBytes` 只在真写后推进、无重复；
- 假 channel：`write` 抛 `ClosedChannelException` → 断言连接被关闭、无自旋（用 latch + 500ms 上限）；
- 队列非空时 `forwardToSocks` 返回 0 且不 ACK。

## 第四批 (2026-11-25 · 三个产品/设计项)

| 项 | 落地 |
|---|---|
| **② `ExitHealth.Failed`（方案 A）** | `startExit` 失败**保留条目**：`health=Failed`、`lastError`、`failTotal++`，仍回收半成品资源；`selectExit` 天然跳过（只认 Ready）；`ExitHealthEvaluator` 不复活；重复启动时 Failed 条目先摘除再重建（否则会假 success 永远卡死）。`exitsState` 让 UI/快照可见 |
| **P1-16 出口状态 chip** | `TunnelManager.exitsState: StateFlow<List<ActiveExit>>`；多出口页每行显示 `启动中/就绪/降级/失败/已停止 · N 连 · 失败 N`（4 语言资源）。**连接计数不逐连接发布**——否则 UI 每次新建 TCP 都重算"出口×规则行数"引用数 |
